## 先に結論の数字だけ

- 総投稿数: **1,271本**(X 456 / Bluesky 529 / note 139 / YouTube Shorts 126)
- 期間: 2026年3月26日〜8月上旬(約4.5ヶ月・ほぼ無人)
- Xのインプレッション**中央値: 29**(公式APIで直近100本を実測)
- 100インプ未満: **92/100本**
- リポスト: **直近100本で0件**(4.5ヶ月の全456本でも合計7件)
- フォロワー: **139人**(月+6人ペース)
- 月額コスト: **約$48**(X API $41が85%)

生成AIでSNS運用をほぼ全自動化するシステムを個人開発して、自分のアカウントで回し続けた結果がこれです。数値は自作の計測基盤(公式APIの日次スナップショット)とDB集計によるもので、僕の1アカウントの観測です。

この記事は「AIでSNS自動化は儲かる」でも「やめとけ」でもなく、**回し続けて計測したら見えた構造**の話です。LLMで何かを自動化しようとしている人には心当たりが出てきそうな欠陥パターンを、実測値つきで置いていきます。

## 作ったもの

構成はよくある形です。

```
収集(バズ投稿/競合) → 分析(パターン学習) → 生成(Gemini) → 品質チェック → 予約投稿
        ↑                                                            ↓
        └──────────── メトリクス回収(公式API) ←──────────────────────┘
```

- GitHub Actions の cron 20本強で毎日全自動
- 投稿はX公式API。バズ投稿の収集はSocialData API
- 生成した投稿は品質スコアとNGワードフィルタを通して DB(Supabase)に貯め、時間帯に合わせて消費
- 反応(いいね/インプ)を回収して「効いたパターン」を学習し、次の生成プロンプトに注入する自己改善ループ

ちゃんと「学習して自己改善するループ」まで組みました。**そのループが機能していなかった**、というのがこの記事の本題です。

:::message
規約について: 投稿・収集・メトリクス回収はすべて公式API(有償)経由です。開発の途中でブラウザ自動化(Playwright+Cookie)を使っていた機能が2つありましたが、Xの利用規約に反するため撤去しました。また「APIで実行できる」ことと「規約上推奨される」ことは別です。自動投稿を運用する場合はXのAutomationルールを確認してください。
:::

## 「内容が悪いんだろう」と思って中身を精査したら、構造欠陥が7つ出てきた

インプが伸びない期間が続いたとき、最初に疑ったのは生成内容でした。プロンプトを何度も改善しました。変わりませんでした。

そこでコードとDBを実測ベースで総点検したら、エラーを一度も出さずに毎日緑で回り続けている欠陥が次々出てきました。全部「テストは通る・ログは健全・結果だけが間違っている」タイプです。

### 欠陥1: 「人気順ソート」は実は「古い順ソート」

リプライで露出を稼ぐ機能が、`min_faves:100`(いいね100以上)で検索して`likes`降順で返信先を選んでいました。

いいねは時間で溜まります。つまり**2時間前の熱い投稿は構造的に選ばれず、勝つのはいつも大昔の投稿**。実測したら、返信していた相手は **758日前・202日前・114日前**のツイートでした。2年前の投稿に返信して、誰が見るのか。

修正は「いいね数」ではなく **velocity(いいね数 ÷ 経過時間)** でランクすること。`since_time`で直近6時間に絞った上でvelocity順にしたら、返信先は中央値3時間前になりました。

**人気度でソートしているつもりの箇所は、蓄積量でソートしている＝古さでソートしている。** 収集系を書いている人は一度確認する価値があります。

### 欠陥2: LLMの自由記述ラベルは永遠に収束しない

投稿の「勝ちパターン」をLLMに命名させて学習テーブルに貯めていました。判定は`pattern_name`の完全一致。

LLMは毎回ちょっと違う名前を付けます。「共感型ストーリーテリング」「共感ストーリー型」「ストーリーテリング(共感)」──全部別行です。

実測: **投稿225本に対して506ラベル**。サンプル3件以上あるラベルは30個だけ。統計として何も学習できていないのに、ログには「227投稿を分析、17パターンが基準到達」と健全そうな行が毎日出ていました。

修正は正規化関数を1枚挟むこと。ただし**書き込み側だけでなく、集計・スコア書き戻し・減衰の全経路に同じ正規化を通す**必要があります(1箇所でも生の名前が残ると、そこだけ0行更新の無音バグになる)。

### 欠陥3: 学習結果の注入がdiversity collapseを起こしていた

「効かなかったパターン」を禁止リストとして生成プロンプトに注入していました。気づいたときには**禁止493件・13,597文字(約6,000トークン)を毎回注入**していました。

禁止が多いほど出力の探索空間は縮みます。つまり**マンネリを防ぐために貯めた学習データが、マンネリの最大の生産者になっていた**。

さらに悪いことに、その493件の大半は欠陥2のラベル分裂で生まれたサンプル数1〜2件の「証拠なしパターン」でした。修正後は「サンプル3件以上のみ・上限12件」で、注入は129トークンまで縮みました。

### 欠陥4: 生成 > 投稿の不均衡は、すべての改善を44日遅らせる

これが一番効いていました。

生成が1日14.4本、投稿が1日7.4本。差分は「在庫」としてDBに積まれ、消費は`ORDER BY created_at ASC`(古い順)。

実測: **在庫620件=89日分。7月23日に公開されていたのは5月26日〜6月9日に生成された投稿**でした。生成→公開の遅延は中央値44日。

つまりプロンプトをどれだけ改善しても、**成果への反映は約1.5ヶ月後**。しかも症状は「生成器の不具合」と見分けがつきません。僕は生成器を5回改修した後にこれに気づきました。

修正は賞味期限です。14日を超えた下書きは自動失効。ただし一度掃除しても、生成>投稿の不均衡が続く限り約88日で再発するので、**弁(期限)を常設することが本体**です。

### 欠陥5: 「反応ゼロ」をスキップする＝生存者バイアスをコードで実装している

メトリクス回収処理が、全指標0の投稿を「削除済みだろう」とみなして更新をスキップしていました。

結果、**負けた投稿だけが学習コーパスから構造的に消える**。学習データは「そこそこ勝った投稿」だけになり、勝因分析が永遠に歪みます。これもエラーは一度も出ません。

### 欠陥6: 分母の欠測を0として扱うと、順位付けが壊れる

エンゲージ率を`(likes+RT)/views`で計算していましたが、片方のプラットフォーム(Bluesky)には views に相当する指標が存在しません。コードは欠測を0に丸めていました。

0除算を避けた結果の下限値 × 足切り閾値の組み合わせで、**平均4.3いいねの好調パターンが「学習データなし」として恒久足切りされ、平均0.8いいねのパターンが最優先注入されていた**のを実測しています。

欠測は0ではなくnullで伝播させて、順位付けから除外する。基本ですが、複数プラットフォームを跨いだ瞬間に踏みます。

### 欠陥7: APIの権限はドキュメントではなく実測でしか分からない

X API v2(self-serveの有償プラン・**2026年7月時点の僕の環境での実測**。プランや時期で変わる可能性があります):

| 操作 | 結果 |
|---|---|
| 自分の投稿 | 200 |
| 他人への返信 | **403** |
| `quote_tweet_id`での引用 | **Enterprise限定** |
| 本文にツイートURLを書いた通常投稿 | **201・引用RTとして成立** |
| リポスト | 200 |

少なくとも僕が読んだ範囲のドキュメントからは、この403は事前に読み取れませんでした。結果、「他人への返信403」に気づかないまま、**リプライ下書きを量産する機能が、構造的に1本も投稿できない下書きでDBを埋めていた**時期があります。

おまけに、2023年に公開されたXのレコメンドアルゴリズムのソースコードでは、重みは リポスト1.0・返信13.5・著者が返信を返すと75・いいね0.5 とされています(現在も同一という保証はありません)。この重みが今も近いなら、**APIで打てる手(投稿)と、アルゴリズム上で効く手(会話)が逆**ということになります。自動化の設計を始める前に知りたかった。

## 7つ全部直した。で、インプは動いたのか

動きませんでした。

| | 修正前 | 修正後2週間 |
|---|---|---|
| インプ中央値 | 30 | 39 → 23 |
| 100インプ以上の割合 | 5.4% | 16.7% |
| リポスト | ほぼ0 | 月1件 |

100インプを超える「そこそこ見られる投稿」の率は3倍になりました。見た人のいいね率はもともと5.2%と悪くない。**内容は改善している。でも中央値は1ミリも動かない。**

理由はおそらく単純で、**フォロワー139人のアカウントの投稿は、そもそもほとんど誰のタイムラインにも乗らない**からです。インプ中央値29というのは、内容のA/Bテストが統計的に成立しない水準です。分母がなければ分子の改善は観測できない。

なお、修正前後で期間もフォロワー数も統制していないので、この比較は厳密な因果ではありません。それでも4.5ヶ月の観測から言えるのは、**少なくとも僕のケースでは、ボトルネックは内容ではなく分布(distribution)だった**ということです。そして分布を動かす手段(会話・被リポスト・外部流入)は、APIの権限とプラットフォーム規約のせいで、ちょうど自動化できない領域に集中しています。

## 学び

- **「エラーゼロで毎日回る」と「正しく動いている」は別物。** 今回の7欠陥は全部、ログが健全なまま結果だけを壊していた。自動化ループには「回っているか」ではなく「回った結果が正しい方向か」の監視が要る
- **自己改善ループは、評価関数が1箇所壊れると自己悪化ループになる。** しかも学習データが貯まるほど悪化が加速する(欠陥2→3の連鎖)
- **在庫を持つパイプラインは、改善のフィードバックが在庫日数ぶん遅延する。** 遅延した改善は「効いていない改善」と区別がつかない
- **完全自動化で埋められるのは「量」だけで、SNSで効くのは「会話」だった。** 打てる手と効く手が逆なら、その自動化は構造的に頭打ちになる

このシステム自体は今も動いています。唯一残ったのは計測層で(公式APIで全投稿の非公開メトリクスを日次スナップショット、$0.001/件)、この記事の数字が実測で出せるのはそのおかげです。

負け戦のデータでも、計測してあれば記事が1本書ける。それが4.5ヶ月と$200ちょっとで買った教訓です。
